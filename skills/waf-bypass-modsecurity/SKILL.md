# ModSecurity WAF Bypass

## Crown Jewel Targets

- Servers with ModSecurity at low paranoia levels (PL1-PL2)
- CRS rulesets with default configurations
- Applications where ModSecurity is in detection-only mode

## Attack Surface Signals

- `X-Scanner` header confirms ModSecurity CRS
- Response code 403 with "ModSecurity Action" in body
- "This error was generated by Mod_Security" in block page
- Custom error pages with `mod_security` references

## Step-by-Step Methodology

1. Confirm ModSecurity presence: check for `X-Scanner` header or error messages
2. Determine CRS paranoia level (PL1-PL4)
3. At PL1: Simple comment injection often works
4. At PL2: Need encoding + comment injection
5. At PL3: Need advanced obfuscation and alternative syntax
6. At PL4: Need novel techniques; behavioral rules are active

## SQLi Bypass Payloads

```sql
-- Comment injection (bypasses PL1)
1' UN/**/ION SEL/**/ECT 1,2,3--

-- Hex encoding
1' UNION SELECT 0x61646D696E,2,3--

-- URL encoding + comments
1%27%20UN/**/ION%20SEL/**/ECT%201,2,3--

<!-- XSS with encoding -->
<svg%20onload=alert(1)>
```

## Common Root Causes

- ModSecurity CRS PL1 and PL2 rely heavily on regex signatures
- Comment injection `/**/` breaks regex patterns
- Encoding differences between WAF and backend
- Paranoia level trade-off: higher detection = more false positives

## Bypass Techniques

- PL1 bypass: comment injection, case toggling
- PL2 bypass: encoding + comments, alternative keywords
- PL3 bypass: advanced obfuscation, protocol manipulation
- PL4 bypass: novel techniques, behavioral rule evasion
